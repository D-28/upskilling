### [A] Loop vs. Graph Engineering Clearly Explained
- **Source:** [`https://x.com/Sumanth_077/status/2089728772979544288`](https://x.com/Sumanth_077/status/2089728772979544288)
- **Author & Date:** Sumanth (`@Sumanth_077`) · Aug 18, 2026 (3 months old as of Nov 2026)

**What it covers:**
In July 2026, OpenClaw creator Peter Steinberger (`@steipete`) joked on X: *"Are we still talking loops or did we shift to graphs yet?"* Hamel Husain piled onto the joke with an article declaring loop engineering dead, and within 48 hours courses and roadmaps popped up around "graph engineering." Sumanth steps back to separate the marketing rebrand from the real engineering choice:
1. **What a Loop is:** An autonomous cycle where one agent plans, acts, and verifies repeatedly without a human typing the next prompt (e.g., Linear's Loops for automated bug triage/doc updates).
2. **What a Graph is:** A layer above loops where multiple nodes (each a task or loop) are wired together with explicit edges and state handoffs. Frameworks like LangGraph (Jan 2024), Microsoft AutoGen, and Google ADK had already been doing this for over a year before the buzzword caught fire.
3. **The key relationship:** A loop is not the opposite of a graph—**a loop is a 1-node graph.** You start with one loop and only split into a graph when the work genuinely breaks into parallel tracks, needs separate contexts/memory/permissions per role, or requires explicit auditable control flow.

**Noise vs. Signal Assessment:**
- **Noise:** The "loop vs. graph" debate itself, and the article acting partly as a funnel to the author's newsletter/repo.
- **Keep:** One crisp axiom—**"reaching for a graph when your loop is broken doesn't fix the loop; it gives you a more complex system with the same underlying problem."** Everything operational in **A** is covered much deeper in **C**.

### [B] How the Claude Code Team Thinks About Verification
- **Source:** [`https://x.com/addyosmani/status/2122590683055993308`](https://x.com/addyosmani/status/2122590683055993308)
- **Author & Date:** Addy Osmani (`@addyosmani`, Anthropic Claude Code team) · Nov 17, 2026

**What it covers:**
Roughly **90% of the Claude Code team's code is written and reviewed by Claude**. At that volume, human line-by-line diff review breaks completely. The team shifted human engineering time from *writing code and reading every diff* to **defining "done," building un-gameable verification loops, and reviewing execution evidence**—which is what makes running dozens or hundreds of agents in parallel safe.

Key concrete practices from the article:
1. **Invest in 3 test types agents can't easily fool** (avoid flaky tests that train agents to retry, and slow tests that force oversized batches):
   - **End-to-End (E2E) tests (Priority #1):** Drive real user workflows (e.g., add to cart → checkout → confirmation) using Chrome DevTools Protocol (CDP), mobile MCP simulators, desktop computer use, or local API harnesses, guided by a feature map rubric. Unit tests can pass while the real feature is broken; E2E tests produce concrete pass/fail and visual screenshot evidence.
   - **Property-based tests:** Using libraries like `fast-check` (JS/TS), `Hypothesis` (Python), or `proptest` (Rust), assert invariants that must *always* hold (round-trip `decode(encode(X)) == X`, non-negative account balances, idempotency, equivalence to a naive implementation) across thousands of generated inputs that don't share the coding agent's blind spots.
   - **Differential tests:** For migrations, feed random inputs or sampled production traffic to *both* old and new systems, normalizing noise (like whitespace) and tracking approved intentional diffs.
2. **Verification means actually running the app:** Codify how to boot and smoke-test the app in a repo `.claude/skills/verify` skill and stress-test it until rock solid.
3. **3-strike human escalation:** If an automated verification check fails across **3 repair rounds**, Claude stops looping and brings in a human.
4. **Diff-triggered reliability checklists:** Anthropic maintains a **39-item reliability checklist** where each item has a diff-readable trigger (e.g., if session storage/message types change → verify `--resume` safely loads older transcripts missing the new field). The reviewer reads the diff and checks only the **3–10 matching items**—no one has to memorize past outages.
5. **Anti-gaming review rules:**
   - Read `REVIEW.md` strictly from the **base/default branch**, never from the PR branch (a change cannot rewrite the rubric judging it).
   - Separate writer and grader (a separate rubric grader boosted structured file generation by up to 10 points).
   - Tune **one primary reviewer** with multi-round failure context rather than stacking extra reviewers; tag findings as `Important`, `Nit`, or `Pre-existing`.
   - Reserve reviews for stable commits (not moving targets) and run cheap lint/test/build checks locally before pushing via hooks or `/goal`.
6. **Safe gate rollout (`off → observe → enforce`):** Stamp every commit with how it was verified (including `"none"` so unverified commits are queryable). Gate commits missing `/code-review` or `/verify` in **observe mode** first to measure false positives, then turn on **enforce mode**—allowing a commit through after **2 blocks** if the commit message explains why, so agents never get deadlocked.
7. **Evaluate reviewers empirically & prune:** Measure rules against real reverted PRs, maintainer rejections, and size-matched clean controls (evaluating recall separately at raw findings, post-verification, and final review). Promote recurring misses (seen in ≥2 PRs) only after **3 agents fail to disprove the rule** and a human approves the PR—or replay 3 bug finders on an incident PR (if ≥2 find a bug missed on a small diff, codify it in `REVIEW.md`). Ban skipping/sleeping/retrying flaky tests (fix root cause or delete with reason), and prune stale `.md` rules routinely.

**Verdict:** Highest-ROI playbook in the batch for both Staff SWE (org verification infrastructure) and FDE (shipping reliable migrations/systems quickly). See [`playbooks/verification-engineering.md`](../playbooks/verification-engineering.md).

### [C] Harness, Loop, Graph: The 3 Layers That Decide If Your AI Agent Works
- **Source:** [`https://x.com/0xWhitemon/status/2119430401701621865`](https://x.com/0xWhitemon/status/2119430401701621865)
- **Author & Date:** Whitemon (`@0xWhitemon`) · Nov 8, 2026

**What it covers:**
Instead of repeating the losing cycle (*rewrite prompt → switch model → add `IMPORTANT` in ALL CAPS*), Whitemon splits the sprawling 2025–2026 agent checklist (skills, hooks, MCP, memory, permissions, subagents) into **three clean engineering layers**:
- **Harness (`environment` — what the agent *can* do):** Everything left on the architecture diagram if you erase the LLM. Built from 6 parts:
  1. *Contract* (`goal`, `inputs`, `output`, `constraints`, and most importantly **`done_when`**).
  2. *Map* (a short root `AGENTS.md` pointing to deeper docs—context is an attention budget, not storage).
  3. *Tools* (10 narrow tools beat 40 overlapping ones; explicit inputs, failure states, and permission tiers).
  4. *Memory* (context window is RAM; `PROGRESS.md`, files, and git commits are disk so sessions survive crashes/resets).
  5. *Walls* (permissions enforced *outside* the model—never let the same system invent the plan, approve the risk, and execute the side effect).
  6. *Traces* (context loaded, tools called, changes, test runs, retries, cost).
  - **Key tactic — "Write It Twice":** Write important rules once as prose `GUIDE` in `AGENTS.md` and a second time as an un-bypassable `CHECK` in CI/lint (e.g., lint fails if `src/ui/**` imports `src/db/**`).
- **Loop (`evidence` — how it knows it's *right*):** *"Don't loop on confidence, loop on evidence."*
  - **Evidence hierarchy:** Deterministic (`exit 0`, build/schema passes) > Observable (trace proves the test ran) > Independent (reviewer in separate context) >>> Self-report (`"looks good"`, `"should pass"`).
  - **Structured feedback instead of `"Red"`:** Emit `FAILED`, `EXPECTED`, `SAW`, `FENCE` (allowed edit scope), and `DEAD ENDS`. Break and escalate immediately if `evidence.saw` matches a prior dead end ("same result twice" exit).
- **Graph (`coordination` — what happens *next*):** Nodes, real edges, and state between nodes. Reach for a graph *only* when one loop breaks.
  - **Early-Start Test:** For every arrow `A → B`, ask what breaks if `B` starts before `A` finishes. If nothing breaks, delete the arrow and parallelize.
  - **4 Cuts:** (1) Split where things fail independently; (2) Give every worker its own fresh context; (3) **If the answer should never vary (merge, sort, dedupe, count), use deterministic code, not an LLM**; (4) Freeze passed nodes as read-only so failures only rerun the failed node.
- **Undo-Price Gating:** Gate autonomy by blast radius rather than model confidence scores:
  - `ONE-CLICK UNDO` (docs, tests, one function) → ships on green.
  - `CLEANUP UNDO` (shared helpers, auth, schemas) → green + trace + second opinion.
  - `NO UNDO` (migrations, deletes, emails, money) → **a human signs** (never an LLM confidence threshold).
- **Diagnostic & Learning Matrix:** Maps symptoms straight to layers (copy-pasting → harness tools; repeating dead tries → harness memory; false "done" → loop check; burning budget on same error → loop exits; slow serial run → graph shape; cascading reruns → graph gates; weekly recurring bug → upgrade infrastructure, not the prompt) and calls out **5 Mistakes That Kill Agent Systems**.

**Verdict:** Essential companion to **B**. See [`playbooks/harness-loop-graph.md`](../playbooks/harness-loop-graph.md) and [`templates/undo-price-gating.md`](../templates/undo-price-gating.md).

### [D] Claude Code "Code Mode" Launch
- **Source:** [`https://x.com/ClaudeDevs/status/2122801681939234950`](https://x.com/ClaudeDevs/status/2122801681939234950) (links to `code.claude.com` docs)
- **Author & Date:** Anthropic (`@ClaudeDevs`) · Nov 17, 2026

**What it covers:**
Announces **Code Mode**, an experimental capability in Claude Code (`v2.1.323+`, opt-in via `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1` or `~/.claude/settings.json`).
- **The problem it solves:** Standard agents call tools one turn at a time (`Read` → dump whole file into context → `Bash rg` → dump 300 lines → `Edit` → repeat). This bloats the context window with raw tool/MCP payloads and burns round-trip latency.
- **How Code Mode works:** Instead of sequential tool calls, Claude writes a **single JavaScript script** run in a local REPL that chains `Bash`, `Read`, `Edit`, and connected **MCP servers**, fans out parallel calls, filters/aggregates data locally, and returns only the distilled result to Claude's context window. Long-running scripts can run in the background (up to **2 hours** in `auto`/`bypassPermissions` mode) while you keep chatting; pressing `Ctrl+O` reveals the collapsed generated code blocks.

**Crucial Nov 2026 Caveats (Don't miss these):**
1. **Experimental & surface-locked:** Interactive terminal CLI only. Does **not** work in `-p` (print mode), Agent SDK, VS Code extension panels, Desktop app, or cloud sessions.
2. **Incompatible features & enterprise limits:** Cannot run with **Agent Teams**, disables Remote Control / Claude in Chrome / computer use, and is blocked on HIPAA/Zero Data Retention (ZDR) configurations and third-party gateways (AWS Bedrock, GCP Vertex, Microsoft Foundry).
3. **Hook & MCP security impact:** Existing shell/tool-level `PreToolUse` hooks don't automatically catch commands buried inside generated JS unless updated to inspect `tool_input.code` (or using auto-mode's script safety classifier). Combining arbitrary script execution with external MCP servers increases prompt-injection / data-exfiltration risk without allowlists and sandboxing.

**Verdict:** Even if you can't flip this flag on a regulated work laptop today, the *pattern*—doing multi-step data gathering/filtering in code outside the LLM context window—is the future. See [`playbooks/programmatic-tooling-mcp.md`](../playbooks/programmatic-tooling-mcp.md) and [`hooks/verify-gate-observe.md`](../hooks/verify-gate-observe.md).

### [F] Choosing a Claude Model & Tuning Reasoning Effort
- **Source:** [`https://x.com/ClaudeDevs/status/2119898687803621427`](https://x.com/ClaudeDevs/status/2119898687803621427) (links to `claude.dev` blog)
- **Author & Date:** Anthropic (`@ClaudeDevs`) · Nov 9, 2026 (coinciding with the **Claude Fable 5.2** release)

**What it covers:**
Anthropic's official guide to balancing capability, latency, and token cost across the November 2026 lineup (**Claude Fable 5.2** alongside **Haiku 5.5, Sonnet 5.5, Opus 5.5**, plus restricted **Mythos 5.2**):
1. **Two orthogonal dials — Model vs. Effort:**
   - *Model* fixes the intelligence ceiling and per-token price.
   - *Effort* (`low → medium → high → xhigh → max`) controls dynamic internal thinking and tool-call budget.
2. **Tune effort *before* swapping models:** Diagnose failures first. If the agent rushed or skipped steps, bump **effort** up one notch on the same model. If it over-engineered a simple change, turn **effort down** instead of downgrading the model. Only escalate to a heavier model (e.g., Opus 5.5 → Fable 5.2 at ~USD 8 / USD 40 per MTok) when the lower tier hits a genuine capability ceiling on ambiguous, long-horizon work.
3. **Prompt cache warning:** Changing effort mid-session can invalidate prompt caching, silently multiplying input costs—pick an effort setting per phase/session.
4. **Subagent cost routing:** Plan/architect with a top tier (Fable/Opus), then push well-scoped mechanical subtasks (search, extraction, routing, formatting) down to smaller, faster models (Sonnet/Haiku).

**Verdict:** Vital cost/latency framework for FDE/FDSE production systems and personal quota management. See [`playbooks/model-effort-economics.md`](../playbooks/model-effort-economics.md).

### [G] Watch Me Ship a 21,000-Line Feature with `mattpocock/skills`

**What it covers:**
A ~70-minute real-world walkthrough building a non-trivial thumbnail creator feature (~21,000 lines across stacked PRs) without descending into "AI slop." The secret is **not** fancy prompts—it is a strict **idea-to-ship skill spine** plus aggressive context-window hygiene:
1. **The Skill Spine (`mattpocock/skills`):**
   - `grill-me` / `grill-with-docs`: Forces the agent to cross-examine you until every edge case and design branch is resolved, writing shared vocabulary into **`GLOSSARY.md`** and key choices into **ADRs** (`0:04:42–0:25:36`).

   - `/to-spec` → `/to-tickets` (`0:42:28`): Freeze decisions into a written spec, then slice work into **vertical "tracer-bullet" tickets** (each cutting thin through schema, API, UI, and tests so it is independently demoable and fits in one fresh session).
   - **Compact/Reset → AFK `/implement` + `/tdd` (`0:46:28`):** Run red-green-refactor implementation in clean sessions without re-litigating design.
   - **Stacked PRs → Human review → Retro (`0:48:30–1:08:02`):** Split huge work into reviewable stacked diffs, review cleanly, audit comments, and capture lessons.
2. **Smart Zone vs. Dumb Zone (`0:40:15`):** Even when models advertise 1M+ token windows, practical instruction-following and recall degrade noticeably past **~100K–150K tokens** of accumulated logs, reads, and dead debugging turns (*the Dumb Zone*). Writing `GLOSSARY.md`, ADRs, specs, and tracer-bullet tickets to disk lets you **reset context frequently** so implementation stays inside the *Smart Zone*.

### [H] ASD-STE100 ("STE-80") & The 4-Level Understanding Ladder
- **Source:** [`https://x.com/karpathy/status/2105819303471976479`](https://x.com/karpathy/status/2105819303471976479) (plus follow-on practitioner evaluations by `@j3ffyang` on Oct 20, 2026 and Vishal Mysore on Oct 14, 2026)
- **Author & Date:** Andrej Karpathy (`@karpathy`) · Oct 2, 2026

**What it covers:**
Karpathy observes that as coding and reasoning agents execute larger tasks autonomously, human work shifts *"up the abstractions into oversight and understanding."* The bottleneck is no longer token generation; it is **human comprehension bandwidth**. Default LLM prose works against fast review: it pads answers with conversational filler, rotates synonyms for the same component, and buries conditions or multiple instructions inside long compound sentences.

To fix this, Karpathy outlines a **4-level output escalation ladder** and coins the concept of **"large, custom, discardable software artifacts"** (bespoke interactive tools generated for pennies to understand one problem in 30 seconds, then deleted):
1. **Level 1 — Controlled English (`~80% ASD-STE100` / "STE-80"):** ASD-STE100 (Simplified Technical English, Issue 9) is a 1980s aerospace maintenance manual specification with 53 grammar rules and an ~875-word controlled dictionary designed so non-native speakers never misread a safety-critical step. Because full compliance feels robotic on general explanations, Karpathy prompts for **"80% of the way to ASD-STE100"**:
   - **One name for one thing (Rule 1.11):** Zero synonym drift. Once an item is named in `GLOSSARY.md`, never rotate to near-synonyms (`config` vs. `settings`, `actuator` vs. `control unit`).
   - **One instruction per sentence (Rule 5.2) & hard word caps (Rule 5.1):** `<= 20` words for procedural instructions; `<= 25` words for descriptive sentences (excluding code spans). Split long sentences into two rather than deleting conditions.
   - **Condition-first ordering (Rule 5.4):** Start with the trigger (`"If the check fails, read the log."`), never bury `"if..."` at word 45 of a compound sentence.
   - **Imperative mood & active voice (Rules 5.3 & 3.6):** Write `"Run the linter."` (a checkable rule), not `"the linter should be run"` (passive advice).
2. **Level 2 — Diagrams (Structural Bandwidth):** When component relationships, topology, or state transitions are the bottleneck, replace multi-paragraph prose with a `Mermaid` or `SVG` diagram.
3. **Level 3 — Discardable Interactive HTML Artifacts (Causal / Parameter Bandwidth):** When understanding depends on *"what happens when parameter X changes"*, have the agent generate a self-contained `.html` page with sliders, visualizations, or interactive state steppers.
4. **Level 4 — Custom Procedural Explainer Videos (Temporal / Dynamic Bandwidth):** For complex concepts unfolding over time, generate a 3Blue1Brown-style procedural animation (`Manim` or HTML5 Canvas) paired with synthesized narration.

**The Two-Way Engineering Synthesis (Why This Matters for Agent Harnesses):**
- **Agent → Human (Review Bandwidth `[B]`):** Using `STE-80` + Levels 2–3 in PR walkthroughs, ADR summaries, and verification reports directly lowers the cognitive tax of reviewing high-volume agent output.
- **Human → Agent (Instruction Checkability `[C]`):** Follow-on practitioner testing (`@j3ffyang`) demonstrated an asymmetric win when applying STE structural rules to **`AGENTS.md`, `SKILL.md`, and `REVIEW.md`**. A human reading an ambiguous compound rule can ask a clarifying question; an unattended agent guesses a reading and acts on it. Splitting compound rules into condition-first, single-action sentences and enforcing them deterministically via [`scripts/ste_lint.py`](../scripts/ste_lint.py) ("Write It Twice" `[C]`) eliminates silent instruction skipping.

**Crucial Caveats (Don't Miss These):**
1. **Authority bias — clean prose makes bad facts look true:** In Vishal Mysore's `webSTE100` benchmark, an STE-formatted answer on jump-starting a car battery scored high on readability while omitting which cable connects to positive vs. negative terminals. **Never use `STE-80` without requiring execution evidence (`[B]`, `[C]`) and explicit `UNCONFIRMED` tags.**
2. **Keep the rules, skip the copyrighted dictionary:** The 875-word aerospace word list is copyright-restricted by ASD and counterproductive for software architecture. Apply the structural grammar rules to instructions and technical summaries—never to long-form essays.

**Verdict:** High-leverage addition to both Layer 1 (`AGENTS.md` / `SKILL.md` instruction grammar) and Layer 2/3 (human verification bandwidth). See [`skills/ste-clarity/SKILL.md`](../skills/ste-clarity/SKILL.md) and [`scripts/ste_lint.py`](../scripts/ste_lint.py).

## 3. Connecting the Dots

### The Four Leading-Edge Disciplines (Late 2026)
1. **Attention-Budget, Instruction Grammar & Programmatic Context Engineering (`G + D + C + H`):** Keep sessions in the *Smart Zone* using disk artifacts (`GLOSSARY.md`, ADRs, `PROGRESS.md`, tracer-bullet slices), write unambiguous `STE-80` instructions linted by [`scripts/ste_lint.py`](../scripts/ste_lint.py), and keep noisy tool/MCP outputs out of context via programmatic scripts or plain deterministic code nodes.
2. **Verification & Comprehension Systems Engineering (`B + C + H`):** Shift human effort from reading every diff to defining `done_when`, building E2E/property/differential test harnesses, protecting `REVIEW.md` on the base branch, and escalating output modality (`STE-80` → Diagrams → Discardable Interactive HTML) so human review stays high-bandwidth.
3. **Layered Architecture & Failure Diagnosis (`A + C + E`):** Stop blaming the model or writing longer prompts. Diagnose systematically across **Harness → Loop → Graph → Decoupled Production Runtime** and only add graph/multi-agent complexity when a single verified loop genuinely breaks.
4. **Economics & Risk Governance (`F + C`):** Separate Model from Effort, protect prompt caches, route subagents to cheaper tiers, and govern autonomy by **price of undo** rather than confidence scores.

### Career & Tooling Map
- **Staff SWE lens (org-wide leverage):** Focus on **B + G + C + H**—shared base-branch `REVIEW.md`, diff-triggered reliability checklists, `observe → enforce` commit gates, "Write It Twice" CI checks (including `scripts/ste_lint.py` on `AGENTS.md`/`SKILL.md`), and standardizing `grill → ADR/glossary → tracer-bullet` specs across teams.
- **FDE / FDSE lens (production customer delivery):** Focus on **C + F + E + B + H**—decoupled Brain/Hands architectures with append-only event logs, model/effort/cache unit economics, differential testing for legacy migrations, discardable interactive HTML artifacts for fast customer/domain alignment, and navigating enterprise Bedrock/Vertex/HIPAA/ZDR/MCP boundaries (**D**).
- **In Antigravity (personal):** Use `/grill-me` + `/plan` for **G**, `/goal` + Chrome DevTools MCP for **B**, `generative_ui` + [`skills/ste-clarity/SKILL.md`](../skills/ste-clarity/SKILL.md) for **H**'s interactive HTML artifacts and STE-80 clarity, `run_workflow` for **D/C** programmatic fan-out, and `swarm` for **C**'s parallel isolated contexts.
- **In GitHub Copilot CLI (professional):** Use portable `SKILL.md` skills (`skills/`), `.github/agents/*.agent.md` to separate writer vs. independent reviewer (**B/C**), lifecycle hooks + `scripts/ste_lint.py` for `observe → enforce` verification and instruction gates (**B/H**), and small repo helper scripts that return concise JSON summaries to mimic **D**'s context savings inside enterprise constraints.
